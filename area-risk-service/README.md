# STREEVA — Area Risk Scoring Engine

> **Hyperlocal safety risk scoring for Chennai, India.**  
> A standalone backend module of the STREEVA AI-powered Women's Safety System.

---

## What This Module Does

Given a **latitude**, **longitude**, and **hour of day**, this service returns a **risk score (0–100)** for that location — with a fully explainable breakdown of every contributing factor.

```
GET /area-risk?lat=13.0827&lng=80.2707&hour=22
```

## Why Point-Level Crime Data Isn't Used

In India, **point-level geocoded crime incident data does not exist as open data**. The NCRB (National Crime Records Bureau) publishes only district/city-level annual aggregate counts — not per-incident coordinates with latitude/longitude.

This is a fundamental difference from countries like the US, where open police datasets include per-incident GPS coordinates.

**What we do instead:**

We build a two-layer proxy model:

| Layer | Source | Purpose |
|-------|--------|---------|
| **Macro Baseline** | NCRB 2014 district-level IPC data (data.gov.in) | City-level crime context |
| **Hyperlocal Intelligence** | OSM + Google Places + WorldPop | Feature signals at ~174m hex scale |

The proxy approach is validated qualitatively: *does an isolated service lane at 2am score higher than T. Nagar's main commercial strip at 2pm?* It does — and that is the right check for this kind of model.

## Feature List

| Feature | Source | Formula | Why It Predicts Safety |
|---------|--------|---------|----------------------|
| **Crime Baseline** | NCRB 2014 (data.gov.in) | Violent crimes normalized across TN districts | Historical district-level prior |
| **Isolation Score** | OpenStreetMap (OSMnx) | 50% road type + 30% road density + 20% junction density | Isolated lanes lack natural surveillance |
| **Commercial Density** | Google Places API (New) | Inverted count of OPERATIONAL POIs within 500m | "Eyes on the street" (Jane Jacobs, 1961) |
| **Police Distance** | Google Places API (New) | Sigmoid: 100/(1+exp(-0.001×(d-2500))) | Response time, deterrence |
| **Hospital Distance** | Google Places API (New) | Sigmoid: 100/(1+exp(-0.001×(d-3000))) | Emergency response outcomes |
| **Population Density** | WorldPop 2020 (100m GeoTIFF) | Inverted min-max across Chennai bbox | Dense areas have more witnesses |
| **Time Multiplier** | Config (city_config.yaml) | Multiplicative: ×1.0 (day) to ×1.40 (late night) | Same location, different risk at 2am |

---

## Scoring Formula

```
RawScore =
  0.20 × CrimeBaseline        +
  0.25 × IsolationScore       +
  0.15 × CommercialDensity    +
  0.20 × PoliceDistance       +
  0.10 × HospitalDistance     +
  0.10 × PopulationDensity

FinalScore = clamp(RawScore × TimeMultiplier, 0, 100)
```

All weights live in `configs/scoring_weights.yaml` — editing that file requires **zero code changes**.

**Score classification:**
| Range | Label |
|-------|-------|
| 0–25 | 🟢 Low |
| 26–50 | 🟡 Medium |
| 51–75 | 🟠 High |
| 76–100 | 🔴 Critical |

## Quick Start

### 1. Prerequisites
- Python 3.10+
- Google Places API key (New) — [get one here](https://console.cloud.google.com/)

### 2. Setup

```powershell
# Create virtual environment
cd area-risk-service
python -m venv venv
venv\Scripts\activate

# Install dependencies
pip install -r requirements.txt

# Configure environment
copy .env.example .env
# Edit .env and add your GOOGLE_PLACES_API_KEY
```

### 3. Run data pipelines (one-time setup)

```powershell
# Build NCRB district lookup from bundled dataset
python scripts/ingest_ncrb.py

# Download WorldPop population raster (~3 MB for 1km, ~300 MB for 100m)
python scripts/download_worldpop.py
# Then update WORLDPOP_RASTER_PATH in .env as instructed
```

### 4. Start the service

```powershell
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

Open **http://localhost:8000/docs** for the interactive Swagger UI.

### 5. Test a location

```bash
# Marina Beach (expected: Low risk, daytime)
curl "http://localhost:8000/area-risk?lat=13.0500&lng=80.2824&hour=14"

# Same location at night (expected: higher score)
curl "http://localhost:8000/area-risk?lat=13.0500&lng=80.2824&hour=23"

# Isolated area (expected: High or Critical)
curl "http://localhost:8000/area-risk?lat=12.8815&lng=80.0798&hour=22"
```

### 6. Run qualitative validation demo

```powershell
# Direct (no server needed)
python scripts/demo_locations.py --no-server

# Or against running server
python scripts/demo_locations.py
```

### 7. Run tests

```powershell
pytest tests/ -v --cov=app
```

## API Reference

### `GET /area-risk`

**Query parameters:**

| Parameter | Type | Range | Description |
|-----------|------|-------|-------------|
| `lat` | float | −90 to 90 | Latitude (WGS-84) |
| `lng` | float | −180 to 180 | Longitude (WGS-84) |
| `hour` | int | 0–23 | Hour of day (24-hour) |

**Example:** `GET /area-risk?lat=12.9141&lng=80.1408&hour=22`

### `GET /health`
Liveness check. Returns `{"status": "ok"}`.

### `GET /cache/stats`
Returns disk cache statistics (entry count, size, breakdown by type).

### `GET /docs`
Swagger UI with interactive testing.

## Adding a New City

1. Create `configs/city_<name>.yaml` (copy from `city_config.yaml`)
2. Update: `name`, `state`, `ncrb_district_key`, `bbox`
3. Run `scripts/ingest_ncrb.py` — it already processes all states
4. Run `scripts/download_worldpop.py` for the appropriate state raster
5. Set `CITY_CONFIG_PATH=configs/city_<name>.yaml` in `.env`
6. Restart: `uvicorn app.main:app --reload`

No code changes needed. All city-specific values are configuration.

## Validation Approach

**There is no ground-truth labeled dataset** ("this location is unsafe at time T") for Chennai.

We do NOT report precision, recall, or F1 — those metrics require labels that don't exist.

**Qualitative validation** (run `scripts/demo_locations.py`):
1. Isolated road at 22:00 should score **higher** than T. Nagar at 14:00 ✓
2. T. Nagar (dense commercial) should score **lower** than Vandalur periphery ✓
3. Same location at 23:00 should score **higher** than at 14:00 ✓
4. A location 100m from a police station should score **lower** than one 4km away ✓

This is the correct validation approach for a proxy-signal model. It is explicitly documented as a limitation.
